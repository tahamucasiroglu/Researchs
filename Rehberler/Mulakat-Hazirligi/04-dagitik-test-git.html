§ 1Cache ve Redis

Derin sayfa: C# / .NET · 03 · Redis, Önbellekleme stratejileri.

SoruKısa cevap
Redis nedir? MÜLAKATTA SIKBellekte çalışan anahtar–değer veri deposu; tipler: string, hash, list, set, sorted set, stream. Kullanım: dağıtık cache, oturum, sayaç, rate limit, dağıtık kilit, pub/sub, liderlik tablosu.
In-memory cache ile dağıtık cache farkı? MÜLAKATTA SIKIMemoryCache: süreç içinde, çok hızlı ama her sunucuda ayrı ve yeniden başlatınca kaybolur. Redis (IDistributedCache): tüm örnekler ortak görür, ağ gecikmesi var. HybridCache (.NET 9) ikisini birleştirir.
Cache-aside nedir?En yaygın desen: önce cache'e bak → yoksa DB'den oku → cache'e yaz (TTL ile). Yazmada DB'yi güncelle, cache anahtarını sil (invalidate). Diğerleri: write-through, write-behind.
Cache invalidation neden zor?Veri değişince her kopyayı doğru zamanda güncellemek; bayat veri ile tutarlılık arasında denge. Pratik: kısa TTL + değişiklikte anahtar silme + olayla haber verme.
Cache stampede?Popüler anahtar düşünce yüzlerce isteğin aynı anda DB'ye gitmesi. Çözüm: tek isteğin doldurması (kilit/HybridCache), TTL'e rastgele sapma (jitter), arka planda yenileme.
Redis kalıcı mı?Seçimli: RDB (anlık görüntü) ve AOF (komut günlüğü). Birincil veri deposu olarak değil, genelde cache olarak düşünülür.

§ 2Mesaj kuyruğu

Derin sayfa: 05 · Temel kavramlar, RabbitMQ, MassTransit.

SoruKısa cevap
Neden mesaj kuyruğu? MÜLAKATTA SIKServisleri gevşek bağlamak (asenkron), yük tepelerini tamponlamak, yavaş işi (e-posta, PDF) istekten ayırmak, tüketici çökse bile mesajı kaybetmemek.
RabbitMQ kavramları? MÜLAKATTA SIKProducer → Exchange → (binding + routing key) → Queue → Consumer. Exchange türleri: direct, topic, fanout, headers. Ack ile mesaj onaylanır; onaylanmazsa yeniden teslim. Başarısız mesajlar dead-letter queue'ya.
RabbitMQ ile Kafka farkı? MÜLAKATTA SIKRabbitMQ: mesaj aracısı (broker), mesaj tüketilince kuyruktan çıkar, esnek yönlendirme, iş kuyruğu. Kafka: dağıtık, kalıcı olay günlüğü (log); mesajlar saklama süresince kalır, tüketiciler offset ile okur, partition ile ölçeklenir, yeniden oynatma (replay), çok yüksek hacim, olay akışı.
Teslim garantileri?At-most-once (kaybolabilir), at-least-once (tekrar gelebilir — en yaygın), exactly-once (pratikte "at-least-once + idempotent tüketici").
Idempotent consumer? MÜLAKATTA SIKAynı mesaj iki kez gelirse sonuç değişmemeli: mesaj kimliğini işlenmiş tablosunda tut, varsa atla; ya da işlemi doğası gereği idempotent yap (UPSERT).
Outbox ve inbox?Outbox: DB değişikliği + mesajı aynı transaction'da kaydet, ayrı işlem yayınlar. Inbox: gelen mesaj kimliğini kaydedip tekrarı engelle. MassTransit ikisini de destekler.
Komut (command) ile olay (event) farkı?Komut: tek alıcıya "şunu yap" (SiparisOlustur). Olay: olmuş bir şeyi duyurur, çok abone (SiparisOlusturuldu). İsimlendirme: komut emir kipi, olay geçmiş zaman.

§ 3Mimari: monolit, mikroservis, tutarlılık

Derin sayfa: 04 · Mikroservis kavramları, 05 · Dağıtık sistem teorisi, Dayanıklılık kalıpları.

SoruKısa cevap
Monolit mi mikroservis mi? MÜLAKATTA SIKMonolit: tek dağıtım, basit geliştirme/test/işlem; büyüyünce dağıtım ve ölçekleme zorlaşır. Mikroservis: bağımsız dağıtım ve ölçekleme, ekip özerkliği; bedeli ağ hataları, dağıtık veri, gözlemlenebilirlik, operasyon. Olgun cevap: "modüler monolitle başla, gerçek ihtiyaç doğunca ayır."
Mikroservisler veritabanı paylaşır mı?İlke: servis başına veritabanı (kendi verisinin sahibi). Paylaşılan DB gizli bağımlılık yaratır.
Servisler arası iletişim?Senkron: HTTP/REST, gRPC (Protobuf, HTTP/2, hızlı, iç servisler). Asenkron: mesaj kuyruğu/olay. Çok senkron zincir = dağıtık monolit.
CAP teoremi?Ağ bölünmesi (Partition) olduğunda Consistency (herkes aynı veriyi görür) ile Availability (her istek cevap alır) arasında seçim yapılır.
Eventual consistency? MÜLAKATTA SIKVeri tüm kopyalarda hemen değil ama sonunda tutarlı olur. Mikroservis + olaylarla doğal sonuç; arayüzde "işleminiz alındı" gibi tasarım ister.
Dağıtık transaction nasıl? ORTA2PC (iki aşamalı commit) ölçeklenmez; yerine Saga: her adım yerel transaction + başarısızlıkta telafi işlemi (compensation). Choreography (olaylarla) veya orchestration (yönetici servis).
Dayanıklılık kalıpları?Retry (üstel geri çekilme + jitter), timeout, circuit breaker (sürekli hatada çağrıyı kes), bulkhead, fallback. .NET'te Polly / Microsoft.Extensions.Http.Resilience.
API Gateway?Tek giriş noktası: yönlendirme, kimlik doğrulama, rate limit, toplama. .NET'te YARP, Ocelot; bulutta yönetilen gateway'ler.
Yatay ve dikey ölçekleme?Dikey: daha güçlü makine (sınırlı). Yatay: daha çok örnek + yük dengeleyici; uygulama durumsuz olmalı (oturum Redis'te).

§ 4Docker, CI/CD, bulut

Derin sayfa: 07 · Docker, GitHub Actions, Bulut ve IaC, 09 · Bulut yerel.

SoruKısa cevap
Container ile sanal makine farkı? MÜLAKATTA SIKContainer işletim sistemi çekirdeğini paylaşır, yalnız uygulama + bağımlılıkları paketler: hafif, saniyede açılır. VM tam işletim sistemi taşır: ağır, daha güçlü yalıtım.
Image ile container farkı?Image: salt okunur şablon (katmanlı). Container: image'ın çalışan örneği.
Multi-stage build? MÜLAKATTA SIKDockerfile'da sdk image'ında derle, sonucu küçük aspnet (runtime) image'ına kopyala → küçük ve güvenli son image. .NET SDK dotnet publish /t:PublishContainer ile Dockerfile'sız da image üretebilir.
Docker Compose?Birden çok container'ı (API + PostgreSQL + Redis) tek YAML'la birlikte çalıştırmak; yerel geliştirme için. .NET'te alternatif: Aspire.
Kubernetes'ten ne sorulur? ORTAPod (en küçük birim), Deployment (istenen örnek sayısı, güncelleme), Service (sabit ağ adresi), Ingress, ConfigMap/Secret, liveness/readiness probe, HPA (otomatik ölçekleme).
CI ile CD farkı? MÜLAKATTA SIKCI (Continuous Integration): her push'ta derle + test et, ana dalı her an sağlam tut. CD: Continuous Delivery (her an yayınlanabilir, onayla canlıya) / Continuous Deployment (otomatik canlıya).
Tipik pipeline?restore → build → test → (analiz, güvenlik taraması) → publish / image → staging'e dağıt → onay → production.
Dağıtım stratejileri?Rolling (sırayla), blue-green (iki ortam, trafiği çevir), canary (küçük yüzdeye aç), feature flag.
Bulut temel kavramları?IaaS (VM), PaaS (App Service, yönetilen DB), SaaS; serverless (Azure Functions, AWS Lambda); bölge / erişilebilirlik bölgesi; yönetilen servisler; IaC (Bicep, Terraform); sır yönetimi (Key Vault).
Sırlar nerede tutulur?Geliştirmede User Secrets, sunucuda ortam değişkeni veya Key Vault / Secrets Manager; CI'da şifreli sır değişkenleri. Depoya asla.

§ 5Test

Derin sayfa: 06 · Test türleri, Mock kavramı, Entegrasyon testi, TDD.

SoruKısa cevap
Unit, integration, e2e farkı? MÜLAKATTA SIKUnit: tek sınıf/metot, bağımlılıklar sahte, milisaniye. Integration: gerçek bileşenler birlikte (API + DB), WebApplicationFactory, Testcontainers. E2E: kullanıcı gözünden tüm sistem (Playwright), yavaş ve kırılgan. Test piramidi: çok unit, orta integration, az e2e.
Mock ile stub farkı? MÜLAKATTA SIKStub: sabit cevap döner, durumu test edersin ("şu girdide şu sonuç"). Mock: etkileşimi doğrularsın ("Gonder bir kez çağrıldı mı?"). Diğer test double'lar: fake (çalışan basit uygulama, in-memory repo), spy, dummy.
Moq / NSubstitute?Sahte nesne kütüphaneleri: mock.Setup(x => x.Getir(1)).ReturnsAsync(urun), mock.Verify(x => x.Kaydet(It.IsAny<Urun>()), Times.Once). Yalnız arayüz/virtual üyeler sahtelenebilir → DI + arayüz test edilebilirliği sağlar.
xUnit temel? MÜLAKATTA SIK[Fact] parametresiz test, [Theory] + [InlineData] / [MemberData] parametreli. Her test için yeni sınıf örneği (kurucu = setup, IDisposable = teardown). Paylaşılan kurulum: IClassFixture<T>, ICollectionFixture<T>. Güncel sürüm xUnit v3.
AAA nedir? MÜLAKATTA SIKArrange (hazırla) – Act (çalıştır) – Assert (doğrula). Test başına tek davranış; ad: Metot_Durum_Beklenen.
TDD döngüsü? MÜLAKATTA SIKRed (başarısız test yaz) → Green (geçiren en basit kod) → Refactor (temizle, testler yeşil kalsın). Getirisi: test edilebilir tasarım, güvenli refactor.
BDD?Davranışı iş dilinde tanımlamak: Given–When–Then (Reqnroll/SpecFlow).
Neyi test etmem?Framework'ün kendisini, basit get/set'i, private metotları (public davranış üzerinden test et).
Kod kapsamı (coverage) %100 olmalı mı?Hayır; kapsam kalite göstergesi değil. Kritik iş kuralları ve hata yolları kapsanmalı.
EF Core'u nasıl test ederim?In-memory sağlayıcı gerçek DB davranışını taklit etmez (transaction, SQL çevirisi). Öneri: Testcontainers ile gerçek PostgreSQL/SQL Server veya SQLite in-memory (sınırlı).
DateTime.Now içeren kodu test etmek?Zamanı soyutla: .NET 8+ TimeProvider (testte FakeTimeProvider).

§ 6Git

Derin sayfa: 07 · Git ileri seviye.

SoruKısa cevap
merge ile rebase farkı? MÜLAKATTA SIKmerge: iki dalı birleştiren yeni bir merge commit; geçmiş olduğu gibi kalır (dallı). rebase: dalın commit'lerini hedefin ucuna yeniden yazar; doğrusal geçmiş, commit kimlikleri değişir.
Rebase'in altın kuralı? TUZAKPaylaşılmış (push edilmiş, başkasının kullandığı) dalı rebase etme; geçmişi değişir, ekip arkadaşlarında çakışma olur. Kendi yerel dalını temizlemek için kullan.
Squash merge?Daldaki tüm commit'leri tek commit olarak ana dala almak; temiz geçmiş, ayrıntı kaybı.
cherry-pick?Başka daldaki tek bir commit'i mevcut dala kopyalamak (yeni kimlikle). Örnek: ana daldaki hotfix'i release dalına almak.
Conflict nasıl çözülür? MÜLAKATTA SIKAynı satır iki tarafta değişmişse Git durur, <<<<<<<, =======, >>>>>>> işaretleri koyar. Dosyayı düzenle, işaretleri kaldır, git add, git commit (rebase'de git rebase --continue). Vazgeç: --abort. Sonra derle + test.
reset, revert, restore farkı?revert: geri alan yeni commit (paylaşılmış dalda güvenli). reset: dal ucunu geri taşır (--soft değişiklikler sahnede, --mixed çalışma alanında, --hard siler). restore: dosyayı geri getirir.
fetch ile pull farkı?fetch uzak değişiklikleri indirir, birleştirmez; pull = fetch + merge (veya --rebase).
stash?Yarım değişikliği geçici kenara koymak: git stash, sonra git stash pop.
Branching stratejileri? MÜLAKATTA SIKGit Flow: main + develop + feature/release/hotfix dalları; planlı sürümler, ağır. GitHub Flow: main + kısa ömürlü feature dalı + PR; sürekli dağıtım. Trunk-based: herkes çok kısa dallarla (≤1–2 gün) sık sık main'e birleştirir, yarım işler feature flag arkasında; CI/CD ile en uyumlusu.
İyi commit mesajı?Kısa özet satırı (≈50 karakter, emir kipi) + gerekirse neden açıklaması; tek mantıksal değişiklik. Conventional Commits (feat:, fix:) yaygın.
Yanlışlıkla sır commit ettim?Sırrı hemen iptal et / değiştir (geçmişte kalır); sonra geçmişten temizle (git filter-repo) ve push koruması / gizli tarama aç.
