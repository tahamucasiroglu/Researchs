§ 2Node.js, paket yöneticileri ve monorepo

Tarayıcı tarafına yeni geçen biri için en yabancı kısım çoğu zaman burasıdır. Bir mülakatta "package.json ile package-lock.json farkı nedir" sorusu çok sık gelir. Cevap: package.json izin verilen sürüm aralıklarını ve script'leri tanımlar; package-lock.json tüm bağımlılık ağacının çözülmüş tam sürümlerini ve bütünlük özetlerini (integrity hash) sabitler; npm ci onu birebir uygular. Başka bir ekosistemden geliyorsan köprüler:

  • C#'tan geliyorsan → bu bölüm NuGet + dotnet restore karşılığı; ilişki .csproj ile packages.lock.json ilişkisiyle aynı.
  • Java'dan geliyorsan → pom.xml/build.gradle + Gradle lockfile (dependency locking).
  • Python'dan geliyorsan → pyproject.toml + poetry.lock/uv.lock.
  • Hiçbirini kullanmadıysan → yukarıdaki kalın cevap tek başına yeterli.

§ 3Derleme araçları

Tarayıcı yazdığın JSX'i, TypeScript'i, birbirini import eden yüzlerce dosyayı doğrudan anlamaz. Arada bunları tek (veya birkaç) dosyaya derleyen bir araç vardır (C#'tan geliyorsan: dotnet build ve Roslyn; Java'dan: javac + Maven/Gradle). JavaScript'te işi ikiye bölmüşlerdir: transpiler (dili çevirir) ve bundler (dosyaları birleştirir).

bundler paketleyici

Yüzlerce kaynak dosyayı, bağımlılık grafiğini çözerek tarayıcının indirebileceği birkaç dosyaya indiren araç. Aramada "javascript bundler" yaz; "bundler" tek başına Ruby'nin paket aracını getirir.

§ 4Meta-framework: Next.js ve alternatifleri

React tek başına sadece arayüz kurar: yönlendirme (routing), sunucuda render, veri yükleme, derleme yapılandırması yoktur. Bunları paket halinde veren araçlara meta-framework denir. En yaygını Next.js'tir ve iş ilanlarında "React" yazan yerlerin çoğu aslında Next.js kastediyor.

Next.js gerçekten gerekli mi

Gerekir

  • Sayfaların Google'da çıkması gerekiyorsa (SEO, herkese açık pazarlama/e-ticaret sitesi).
  • İlk açılış hızı ticari olarak kritikse; boş HTML + geç dolan ekran kabul edilemiyorsa.
  • Frontend'in kendi hafif backend'i olacaksa ve ayrı bir API yazılmayacaksa.
  • Ekip zaten Next.js kullanıyorsa; tercih bireysel değil.

Fazladır

  • Ürün giriş ekranının arkasında olan bir yönetim paneli/iç uygulama ise. SEO yok, SSR'ın anlamı yok.
  • Zaten ayrı bir Web API varsa (ör. ASP.NET Core, Spring, Django); Next'in sunucu tarafı ikinci bir backend katmanı yaratır.
  • Ekip Node sunucusu işletmek istemiyorsa; herhangi bir web sunucusuna (IIS, Nginx, Apache) veya statik barındırmaya dosya koymak çok daha basittir.
  • Henüz React öğreniyorsan. Next, React'in üstüne ek kavramlar yığar; ikisini birlikte öğrenmek en sık yapılan hatadır.

Kısaca

Doğru seçim projenin türüne bağlı:

  • Ayrı bir backend API'si var (ör. ASP.NET Core, Spring, Django) ve uygulama giriş ekranının arkasında → çoğu zaman Vite + React; Next.js'i "ne olduğunu bilecek" kadar öğren, kurma.
  • Herkese açık, SEO veya ilk yükleme hızı kritik site → Next.js (veya Astro, React Router framework modu).
  • Ayrı backend yok, küçük/orta tam yığın JS uygulaması → Next.js'in Route Handler ve Server Actions'ı backend görevi görebilir.
  • Ekip zaten Next.js kullanıyor veya iş ilanı Next.js istiyor → "kurma" değil: öğren ve kullan.

§ 11Tarih, saat ve genel yardımcı kütüphaneler

Hangi backend'den gelirsen gel en sinsi hata alanlarından biri budur: JavaScript'in yerleşik Date nesnesi zayıftır ve saat dilimi davranışı şaşırtır. API'nden gelen tarih değerinin tarayıcıda bir gün kayması klasik bir olaydır.

Risk

Sunucu ile tarayıcı arasında tarih taşırken daima ISO 8601 ve UTC kullan (2026-09-04T08:30:00Z). Yerel biçimlendirmeyi yalnızca ekrana basarken yap. Alan yalnızca bir takvim tarihi ise (doğum tarihi, fatura tarihi) saat dilimine çevirme; "YYYY-MM-DD" metni olarak taşı — "bir gün kayması"nın asıl kaynağı genelde budur. Backend'ine göre karşılık:

  • .NET → DateTimeOffset veya DateTime + Kind=Utc; yalnızca tarih için DateOnly.
  • Java → Instant/OffsetDateTime; yalnızca tarih için LocalDate; Jackson'da WRITE_DATES_AS_TIMESTAMPS=false.
  • Python → saat dilimi bilgili datetime (datetime.now(timezone.utc)); yalnızca tarih için date.
  • Go → UTC'de time.Time, RFC 3339 biçimi.
  • Node → Date.toISOString() veya Temporal.Instant.

§ 14Dağıtım ve barındırma

Bir React projesinin üretim çıktısı, sonuçta bir klasör dolusu statik dosyadır (index.html, JS ve CSS). Bunu herhangi bir web sunucusu (IIS, Nginx, Apache), backend'inin statik dosya klasörü veya statik barındırma servisi yayınlayabilir. Bu bilgi, bulut servislerinin pazarlama dilinden kurtulmanı sağlar.

Tek sayfa uygulamasının klasik hatası

Kullanıcı /musteriler/5 adresini doğrudan açtığında sunucu o dosyayı arar, bulamaz, 404 döner. Çözüm: sunucuya "bilinmeyen tüm yolları index.html'e yönlendir" kuralı yazmak (SPA fallback). Mülakatta sorulan somut sorulardan biridir. Nerede yayınladığına göre:

  • ASP.NET Core → MapFallbackToFile("index.html"), çıktı wwwroot'a.
  • IIS → URL Rewrite modülü ve web.config rewrite kuralı.
  • Nginx → try_files $uri $uri/ /index.html;
  • Apache → FallbackResource /index.html veya mod_rewrite.
  • Express → express.static + bilinmeyen rotalarda index.html gönderen son rota.
  • Spring Boot → static klasörü + bilinmeyen rotaları index.html'e forward eden controller.
  • Netlify → _redirects içinde /* /index.html 200.
  • Vercel → vercel.json içinde rewrites.
  • Cloudflare Pages → kökte 404.html yoksa SPA davranışı varsayılan.
  • GitHub Pages → rewrite desteği yok: index.html'in 404.html kopyası veya hash tabanlı router.
  • S3 + CloudFront → 403/404 için index.html'e yönlenen özel hata yanıtı.

Bu sayfada iki yüzden fazla madde var. Hepsini öğrenmeyeceksin. Aşağıdaki sıra, bir backend geliştiricisinin (örnekler .NET; Java, Python, Go için aynı yol) tarayıcı tarafı sorularını geçmesi için gereken asgari yoldur. Frontend veya full-stack JS pozisyonu hedefliyorsan bu yol yetmez; § 1'deki hedef tablosuna göre "Sonra bunlar" listesini de "kullan" düzeyine çıkar.

Önce bunlar (gerçekten yap, kod yaz)

  1. Node LTS kur, npm'i tanı

    package.json, package-lock.json, node_modules, npm run, npx. Beş terim, yarım gün. Bunlar bütün tarayıcı tarafı araçlarının temelidir.

    § 2 · hedef: bir projeyi indirip çalıştırabilmek
  2. Vite ile React projesi aç

    npm create vite@latest, ardından dev ve build komutları, dist klasörü, import.meta.env. Webpack'e hiç girme.

    § 3 · hedef: boş sayfayı ayağa kaldırmak
  3. fetch ile kendi API'ne (ör. .NET) bağlan

    CORS hatasını bilerek al ve backend'inde çöz (ASP.NET Core UseCors; diğer yığınlar § 15'teki karşılık tablosunda); backend'in yoksa MSW veya bir mock API kullan; sonra Vite proxy ile hatayı ortadan kaldır. Alan adı (camelCase/snake_case) uyuşmazlığını, 400 doğrulama hatası cevabını (ASP.NET Core'da ProblemDetails) ve 401 durumunu ele al.

    § 6 ve § 15 · bu sayfanın asıl amacı
  4. JWT'yi nerede saklayacağını cevaplayabil

    localStorage → XSS riski; httpOnly cookie → CSRF önlemi. Refresh token akışını tek paragrafta anlat. Bu, JWT ile çalıştığını söyleyen herkese sorulan sorudur.

    § 15 · kod yazmasan da cevabını ezberle
  5. Çıktıyı backend'inin statik klasörüne (ör. wwwroot) veya statik barındırmaya koyup yayınla

    SPA fallback kuralını kur, base ayarını doğru ver. "React uygulaması aslında statik dosyadır" cümlesini içine sindir.

Backend geliştiricisinin lehine

Bir backend pozisyonunda (ör. .NET, Java, Python) tarayıcı tarafı soruları derinlik değil, farkındalık ölçer. "Vite ile kuruyorum, fetch ile API'ye bağlanıyorum, CORS'u sunucuda çözüyorum, token'ı httpOnly çerezde tutmak daha güvenli ama CSRF önlemi gerektiriyor, çıktı statik dosya olduğu için backend'in statik klasöründen (ör. wwwroot) de yayınlanabiliyor" diyebilen bir aday, bu sayfadaki iki yüz maddeyi ezberlemiş adaydan daha güçlü görünür. Mimari kurgu ve performans bilgisi backend'den taşınır; tarayıcı tarafında da aynı dili konuşmak yeterli. Frontend pozisyonunda ise bu farkındalık başlangıçtır, yeterli değildir.
